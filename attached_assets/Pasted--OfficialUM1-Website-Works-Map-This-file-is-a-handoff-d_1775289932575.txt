# OfficialUM1 Website Works Map

This file is a handoff document for rebuilding the current OfficialUM1 website with the same feature set, page structure, and operational scope, but with a cleaner theme and a less messy implementation.

This document is based on the current root app in this repository:

- Main app root: `app/`, `components/`, `lib/`, `data/`
- Main runtime: Next.js App Router
- Main database layer: MySQL through `lib/db.ts`

Important repo note:

- There is also a nested `officialum1-site-main/` directory in this repository.
- For rebuild purposes, treat the root app as the primary website unless you intentionally want to compare both copies.

## 1. What This Website Is

OfficialUM1 is not only a marketing website. It is a combined:

- digital services agency website
- digital product marketplace
- account/inventory storefront
- checkout and payment system
- customer dashboard and delivery vault
- membership and referral platform
- support and review system
- US business formation funnel
- admin operations panel
- staff panel
- marketplace automation hub for G2G, PlayerUp, and Z2U

In plain terms, the site blends three businesses into one UI:

1. An agency site selling web/SEO/social services
2. A marketplace selling digital accounts, bundles, and memberships
3. An operations back office to manage products, inventory, orders, staff, content, and external marketplace listings

## 2. Current Product Roles

The current code supports these user roles and access patterns:

- Guest visitor
- Buyer
- Seller or staff-like operator
- Admin
- HR/admin operator for employee management

Role behavior in the current implementation:

- Buyer auth is mostly stored in `localStorage` as `buyer_user`
- Staff auth is stored in `localStorage` as `staff_user`
- Admin route protection is handled in `middleware.ts` using the `admin_token` cookie and an optional login gate cookie
- Some server-side APIs still trust user identifiers from the client

For the rebuild, keep the role model, but replace the auth approach with proper server-side sessions.

## 8. Main End-to-End User Flows

### A. Storefront to payment to delivery

1. User lands on homepage or shop
2. User browses products on `/shop`
3. User can:
   - search
   - filter by platform
   - add to wishlist
   - compare items
   - add to cart
4. User goes to `/checkout`
5. Checkout supports:
   - single product purchase
   - cart checkout
   - membership purchase
6. Coupon validation happens through `/api/coupons`
7. Payment submission goes to `/api/checkout/process`
8. Payment methods in current code:
   - Stripe
   - Cryptomus
   - Binance Pay
   - wallet balance
9. After successful purchase:
   - order is created
   - stock is reduced
   - delivery entry is created
   - delivery token page is generated
   - email is sent
10. Customer sees `/order-success`
11. Customer can later open `/my-orders` and `/delivery/[token]`

### B. Buyer auth flow

1. Register on `/register`
2. Verify email through `/verify-email`
3. Login at `/login`
4. Buyer session is stored in `localStorage`
5. Dashboard is available at `/dashboard`

### C. Buyer dashboard flow

Dashboard gives access to:

- wallet overview
- referral earnings
- recent orders
- active deliveries
- notifications
- business formation status
- verification status

### D. Support flow

1. Buyer visits `/support`
2. Creates ticket through `/api/tickets`
3. Admin or staff replies through admin/support tools
4. Buyer sees replies in support center

### E. Review flow

Current review-related flows:

- public review wall on `/reviews`
- testimonial submission on `/share-experience`
- post-order review form on `/shop/review?orderId=...`
- delivery page review submission from `/delivery/[token]`

### F. Membership and VIP flow

- Membership landing page is `/membership`
- Checkout supports membership products directly
- Product detail and listing logic can gate some items based on user membership

### G. Referral and affiliate flow

- `/refer` shows referral program
- Buyer gets a referral code and link
- Dashboard exposes referral metrics
- Affiliate leaderboard endpoints exist
- Wallet conversion and withdraw routes also exist

### H. Business formation flow

1. User lands on `/services/form-business`
2. User chooses jurisdiction and formation options
3. Frontend requests account, offerings, schema, and filing methods from `/api/admin/corptools`
4. User completes wizard
5. Corporate Tools API is used as the back-end service for business setup

### I. Staff flow

1. Staff logs in on `/staff/login`
2. Staff dashboard loads profile and permitted data
3. Staff can manage subsets of:
   - inventory
   - leads
   - marketing
   - support
   - website content
   - finance
   - PlayerUp
   - Z2U
4. Staff profile can be updated through `/api/staff/profile`

## 14. Important Current Implementation Quirks

These are not reasons to remove features. They are reasons to rebuild them more cleanly.

### A. Mixed data model

- Some site content is in MySQL
- Some site content is in JSON files
- Admin tools touch both systems

### B. Very large admin surface

- `/admin/inventory` is effectively a mega application inside one page
- Many unrelated business functions live together in one huge internal screen

### C. Auth/session inconsistency

- Buyer and staff state is client-localStorage-heavy
- Admin is cookie-gated
- Some APIs rely on user IDs passed from the client

### D. Multiple businesses combined

- Agency site
- digital account marketplace
- business formation system
- staff and HR system
- marketplace automation console

This is powerful, but the rebuild should present it in a cleaner information architecture.

### E. Sidecar automation projects in same repo

- Extensions and extra projects live beside the main site
- Rebuild should separate main platform from automation tooling at the architecture level

### F. Verified partial or messy areas worth cleaning in rebuild

- Some admin review moderation payloads do not align cleanly with the API
- Some website/admin content actions are wired through legacy JSON endpoints
- Newsletter sending logic is not cleanly separated from audit/email helpers
- Some admin actions are present in UI but only partially implemented
- Seller dashboard links point to pages that are not fully present
